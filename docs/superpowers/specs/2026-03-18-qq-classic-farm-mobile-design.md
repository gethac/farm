# QQ经典农场移动端复刻设计文档

## 1. 项目目标

本项目目标是使用 React 实现一个面向移动端的 `QQ经典农场` 风格在线游戏，并使用 Node.js 作为后端、WebSocket 作为主要数据查询与同步通道、SQLite 作为数据库。

首版产品不是泛化的“农场游戏”，而是要在移动端上复刻 `QQ经典农场回归版` 的核心体验，重点还原：

- 经典农场视觉语言与氛围
- 核心种植成长循环
- 好友访问、偷菜、帮忙、捣乱等社交玩法
- 商店、仓库、任务、成就、排行榜、消息提醒等常驻系统

本项目不直接搬运原始美术资源，而是采用仿制与重绘策略，在保证整体气质接近经典版本的前提下实现自有资源。

## 2. 已确认范围

### 2.1 复刻基准

- 以 `QQ经典农场` 回归版的产品方向为基准
- 不要求逐像素复刻旧网页布局
- 允许为移动端使用习惯重构交互和布局
- 更重视视觉氛围、经典元素关系、操作反馈和玩法一致性

### 2.2 终端范围

- 首版仅支持移动端 Web
- 不以桌面端作为首版验收对象

### 2.3 账号与社交范围

- 首版包含完整在线账号体系
- 包含注册登录、好友关系、访问好友农场、互动记录、排行榜、消息提醒
- 不做支付与充值系统

### 2.4 功能覆盖范围

首版覆盖“主循环全量 + 主要常驻系统”，不覆盖活动运营系统。

必须包含：

- 注册、登录、基础用户资料
- 我的农场
- 地块解锁与地块状态
- 播种、浇水、除草、除虫、施肥、收获、铲除
- 作物成长、成熟、枯萎
- 商店与仓库
- 出售农产品
- 好友访问
- 偷菜、帮忙打理、放虫捣乱
- 防偷犬
- 经验、等级、金币
- 新手任务、日常任务、成就
- 常驻排行榜
- 消息提醒与互动通知

首版不包含：

- 真实支付、充值、点券体系
- 节日活动、限时活动、运营活动
- 联动内容
- 牧场、餐厅、加工厂等外部系统
- 复杂装饰经营扩展系统

### 2.5 素材策略

- 不直接使用原版资产
- 采用高相似构图、配色和状态表达的重绘方案
- 所有素材需与经典农场视觉语言保持一致

## 3. 推荐架构

项目采用 `单体实时游戏服务` 架构。

### 3.1 前端

使用 React 构建移动端应用，负责：

- 农场主场景展示
- 地块交互
- 商店、仓库、任务、排行榜等弹层与页面
- 好友列表与访问入口
- 数值飘字、提示气泡、状态图标等经典反馈

前端使用：

- HTTP 完成注册、登录、资源初始化等低频入口
- WebSocket 完成游戏内主要查询、操作提交、状态同步与消息推送

### 3.2 后端

使用 Node.js 实现单体服务，一个进程同时承载：

- 鉴权与会话
- 游戏规则计算
- 好友与社交逻辑
- 任务成就与排行榜
- WebSocket 路由与推送
- 定时刷新与低频结算

### 3.3 数据层

使用 SQLite 作为首版数据库，负责存储：

- 用户与账号资料
- 农场与地块状态
- 作物实例
- 仓库物品
- 好友关系与互动记录
- 任务成就进度
- 排行榜快照与统计
- 消息通知

### 3.4 架构原则

- 保持单体部署简单性
- 在单体内部严格划分模块边界
- 所有关键玩法规则以服务端为准
- WebSocket 作为主要业务通道，保证前端状态模型一致

## 5. 移动端视觉与交互设计原则

### 5.1 视觉目标

移动端实现的目标是：用户在手机上操作时，能明确感知这是 `QQ经典农场` 的移动端版本，而不是普通农场题材应用。

### 5.2 视觉还原原则

- 保留天空、远景、田地、地块、宠物、浮层等经典场景层次
- 维持偏网页游戏时代的高饱和、拟物化 UI 气质
- 使用明显图标与飘字表达干旱、长草、生虫、成熟、可偷、守护等状态
- 所有仿制素材在配色、轮廓、信息密度上贴近经典版本

### 5.3 移动端交互改造原则

- 主农场页作为默认核心页面
- 顶部显示头像、等级、金币、经验等关键状态
- 底部提供商店、仓库、任务、好友、排行榜等核心入口
- 地块操作采用点击后弹出快捷操作面板的形式
- 好友栏改造成横滑列表或侧边抽屉
- 次级信息按需展开，避免在移动端堆叠过多常驻文本

### 5.4 首版交互表现要求

- 地块点击反馈必须清晰
- 金币、经验、收获、帮助、偷取等行为要有明显的动画或飘字反馈
- 成熟、异常状态、守护状态需具备一眼可识别的视觉标志

## 6. 核心数据模型

### 6.1 用户

用户数据包含：

- 账号标识
- 昵称
- 头像
- 等级
- 经验
- 金币
- 创建时间
- 最近在线时间

### 6.2 农场

每个用户拥有一个主农场，记录：

- 用户 ID
- 土地总数
- 已解锁地块数量
- 守护犬状态
- 农场基础外观配置

### 6.3 地块

每块地独立记录：

- `slotIndex`
- `lockState`
- `soilState`
- `cropInstanceId`
- `grassLevel`
- `wormLevel`
- `waterLevel`
- `lastCalculatedAt`
- `protectedUntil`

设计目标是支持服务端按时间差对每块地进行状态重算，而不是依赖高频数据库更新。

### 6.4 作物实例

作物必须作为独立实例存储，包含：

- 作物类型
- 播种时间
- 各成长阶段时间点
- 成熟时间
- 枯萎时间
- 预计产量
- 当前健康系数
- 已被偷取数量
- 剩余可收数量

这样可准确支撑偷菜、帮助照料、成熟与枯萎判定。

### 6.5 背包与仓库

首版采用统一库存模型，记录：

- 物品类型
- 物品 ID
- 数量
- 所属用户

通过类型区分种子、功能道具、农产品、奖励物品。

### 6.6 社交数据

包括：

- 好友关系
- 好友申请
- 访问记录
- 偷取记录
- 帮助记录
- 消息与留言记录

### 6.7 任务与成就数据

采用“定义”和“用户进度”分离的方式设计，避免后续扩展困难。

## 7. 成长结算与实时同步

### 7.1 成长结算策略

不为每块地创建常驻定时器。服务端采用 `按需重算 + 必要时持久化` 策略。

触发结算的时机包括：

- 用户进入自己农场
- 用户进入好友农场
- 用户对地块执行操作
- 后台低频轮询补发提醒与同步任务状态

该策略的目标是：

- 降低 SQLite 写压力
- 保证状态可信
- 让成长与异常状态随时间自然推进

### 7.2 WebSocket 通道设计

WebSocket 为游戏主要业务通道。

客户端在连接后完成鉴权，随后通过消息协议进行查询与操作。

典型请求消息包括：

- `farm:getMine`
- `farm:getUser`
- `farm:operate`
- `shop:list`
- `inventory:list`
- `friends:list`
- `tasks:list`
- `ranking:list`

服务端通过 WebSocket 返回：

- 页面初始化所需快照
- 操作结果
- 增量事件

### 7.3 主动推送事件

服务端主动推送至少包括：

- `farm:slotUpdated`
- `farm:cropMatured`
- `inventory:changed`
- `task:updated`
- `task:claimable`
- `social:interactionReceived`
- `ranking:changed`
- `notice:new`

### 7.4 同步原则

- 查询和操作都通过统一协议
- 结果由服务端裁决
- 前端只做操作反馈和状态展示
- 多端同时登录时，以服务端最终事务结果为准

## 8. 后端模块划分

虽然使用单体服务，但内部必须拆分为清晰模块：

- `auth`：注册、登录、会话、鉴权、资料
- `farm`：地块状态、播种、打理、偷菜、守护犬逻辑
- `inventory`：种子、道具、农产品、库存增减
- `shop`：商品列表、购买、出售、价格规则
- `social`：好友关系、好友访问、互动记录、消息
- `tasks`：新手任务、日常任务、成就进度、领奖
- `ranking`：榜单统计与查询
- `realtime`：WebSocket 路由、订阅、推送、连接管理
- `persistence`：SQLite 访问、事务、迁移

各模块之间通过明确的 service 边界通信，避免直接跨模块修改底层数据。

## 9. 错误处理与一致性原则

### 9.1 操作校验

所有地块操作必须校验：

- 用户身份
- 农场归属
- 地块实时状态
- 金币或道具是否足够
- 保护状态
- 偷取次数与偷取上限
- 成熟或未成熟状态

### 9.2 事务要求

涉及多表变更的操作必须使用事务，例如：

- 播种
- 收获
- 偷菜
- 购买
- 出售
- 任务领奖

### 9.3 WebSocket 错误格式

错误返回统一结构：

- `code`
- `message`
- `requestId`
- `details`

以便前端稳定处理提示逻辑。

### 9.4 首版反作弊底线

首版不实现复杂风控系统，但至少要保证：

- 客户端不能伪造成熟时间
- 客户端不能跳过状态校验
- 奖励不能重复领取
- 同一批作物不能被并发重复偷取
- 多端并发操作时以事务结果为准

## 11. 首版完成定义

以下闭环全部可真实运行时，首版视为完成：

- 新用户可注册、登录并完成第一次播种到收获
- 用户可通过持续种植获得成长、经验、等级与金币
- 用户可进入商店、仓库并完成购买与出售
- 用户可添加好友并访问好友农场
- 用户可进行帮忙、偷菜、放虫等经典互动
- 用户可收到互动提醒、成熟提醒与任务提醒
- 任务、成就和排行榜会随用户行为正确变化
- 页面刷新、重新登录、多端切换后数据保持一致

## 13. 后续规划接口

虽然首版不做活动和商业化，但设计上需要预留可扩展空间：

- 商品体系允许未来增加货币类型
- 任务体系允许增加活动任务
- 榜单体系允许增加周期榜
- 消息系统允许增加活动通知
- UI 结构允许未来新增入口页签

这些扩展预留不应影响首版范围，也不应引入首版不需要的复杂实现。

## 14. 首版硬性技术约束

本节为实施阶段的非协商要求，后续计划不得偏离：

- 前端必须使用 React
- 后端必须使用 Node.js
- 实时同步必须基于 WebSocket
- 首版数据库必须使用 SQLite
- 首版服务拓扑必须为单进程单体服务
- 游戏判定逻辑必须全部在服务端执行
- 移动端 Web 是唯一首版交付形态

## 15. 首版规则基线与配置责任

为保证实施计划可拆解、可测试，首版规则采用“规则逻辑固定、数值配置化”的方案。也就是说，规则类型和判定流程在首版内是确定的，具体数值通过配置表或种子数据交付。

### 15.1 规则数据必须交付的内容

实施阶段必须把以下内容作为明确交付物：

- 全量作物目录及其购买价、出售价、成熟时间、枯萎时间、基础产量、经验奖励
- 全量道具目录及其价格、效果、持续时间或使用次数
- 商店商品目录与上架规则
- 帮助次数、偷取次数、保护时长等统一参数
- 任务定义、成就定义、排行榜定义

计划阶段必须把“规则与内容数据录入”视为显式工作项，而不是默认省略。

### 15.2 作物生命周期规则

- 每种作物必须定义：购买价、出售价、成熟时间、枯萎时间、基础产量、经验奖励
- 成长阶段至少包含：播种后、成长中、成熟、枯萎
- 成熟与枯萎时间由作物定义表提供，服务端按时间差结算
- 首版所有作物数值必须来自统一配置表或种子数据，不允许散落硬编码

### 15.3 地块异常与健康系数规则

- 地块异常至少包含：缺水、长草、生虫
- 异常状态由服务端根据时间推进与操作结果判定
- 异常会影响作物健康系数
- 健康系数影响最终产量
- 首版允许将异常影响实现为统一百分比规则，而不是每种作物单独一套规则

### 15.4 收获与收益规则

- 收获时，最终产量 = 基础产量 × 当前健康系数修正后向下取整，且不得低于 0
- 收获后发放农产品、金币收益、经验收益
- 出售价格由作物定义表或商品定义表提供
- 用户等级经验由播种、打理、收获、帮助等事件累计增长

### 15.5 偷菜规则

- 仅成熟且未枯萎作物可被偷取
- 仅好友可执行偷取
- 被守护犬保护或处于保护状态的地块不可被偷取
- 偷取必须扣减目标作物实例的可收数量
- 单个作物实例存在总可偷上限，该上限由作物配置或统一规则提供
- 单个访问者对同一作物实例存在个人偷取上限，该上限由统一规则提供
- 同一批次作物在并发场景下不得被重复结算

### 15.6 帮助与捣乱规则

- 好友可执行浇水、除草、除虫等帮助行为
- 帮助行为可恢复地块状态、改善健康系数，并给帮助者奖励
- 放虫属于捣乱行为，只能对好友农场触发，且需满足目标地块存在作物
- 帮助与捣乱次数上限均由统一配置规则提供

### 15.7 守护与保护规则

- 守护犬提供防偷效果
- 防偷效果必须具备明确的生效状态和结束时间
- 地块或农场的保护持续时间由道具或守护规则提供
- 保护状态必须体现在地块和农场 UI 中

### 15.8 任务与成就规则

- 所有任务和成就必须定义触发条件、进度条件、奖励内容、是否可重复
- 新手任务为一次性任务
- 日常任务按自然日重置
- 成就按累计行为统计，不重置
- 奖励领取必须具备幂等校验

### 15.9 排行榜规则

- 每个榜单必须定义统计字段、统计周期、排序方向、并列处理方式
- 等级榜按等级与经验联合排序
- 金币榜按当前金币排序
- 收获榜按累计收获数量或累计收获价值排序
- 偷取榜按累计偷取数量排序
- 首版允许榜单采用定时刷新快照，不要求实时逐条重排
